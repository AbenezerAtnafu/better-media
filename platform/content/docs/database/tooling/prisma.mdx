Better Media does not use Prisma as its database client. It uses a Kysely-based adapter for the five media tables. The recommended pattern is to use both side-by-side: Prisma for your application tables, the Kysely adapter for Better Media tables, both connecting to the same database.

## Setup

```bash
pnpm add @prisma/client @better-media/adapter-db-kysely kysely pg
pnpm add -D prisma @types/pg
```

Configure them separately:

```typescript
import { PrismaClient } from "@prisma/client";
import { Pool } from "pg";
import { Kysely, PostgresDialect } from "kysely";
import { KyselyDbAdapter } from "@better-media/adapter-db-kysely";
import { schema } from "@better-media/core";

// Prisma — for your application tables
export const prisma = new PrismaClient();

// Better Media — for media tables (same database, separate pool)
const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const db = new Kysely({ dialect: new PostgresDialect({ pool }) });
const bmDatabase = new KyselyDbAdapter(db, {
  config: { provider: "pg" },
  schema,
});

export const media = createBetterMedia({
  storage,
  database: bmDatabase,
  plugins,
});
```

## Migrations

Prisma and Better Media manage separate sets of tables — their migration systems do not overlap.

- **Your application tables** → managed by `prisma migrate`
- **Better Media tables** → managed by the Better Media CLI or `runMigrations()`

Run both as part of your deployment:

```bash
# 1. Apply your app schema
npx prisma migrate deploy

# 2. Apply Better Media schema
npx better-media migrate --yes
```

Or programmatically on startup:

```typescript
import { runMigrations } from "@better-media/core";
import { execSync } from "node:child_process";

// Your app migrations
execSync("npx prisma migrate deploy");

// Better Media migrations
await runMigrations(bmDatabase, schema);
```

## Accessing Media Records from Prisma

Better Media tables are plain SQL tables. You can read them from Prisma by adding them to your `schema.prisma`. Mark them with `@@ignore` or a comment to avoid accidental modifications through Prisma migrations:

```prisma
// schema.prisma

// Better Media tables — managed by Better Media, not Prisma.
// Do NOT include in prisma migrate — use `npx better-media migrate` instead.
model Media {
  id            String    @id
  ownerId       String?   @map("owner_id")
  filename      String?
  mimeType      String?   @map("mime_type")
  size          Int?
  storageKey    String?   @map("storage_key")
  checksumSha256 String?  @map("checksum_sha256")
  status        String?
  visibility    String?
  createdAt     DateTime? @map("created_at")
  updatedAt     DateTime? @map("updated_at")
  deletedAt     DateTime? @map("deleted_at")

  @@map("media")
  @@ignore
}
```

With `@@ignore`, Prisma includes the model in the generated client for queries but excludes it from `prisma migrate` operations.

## Avoiding Migration Conflicts

The biggest risk when using both tools is accidentally running a Prisma migration that tries to create or alter a Better Media table.

- Never add Better Media tables to your Prisma schema without `@@ignore`.
- Run `npx prisma migrate status` before deploying to verify no unexpected migrations are pending.
- Better Media migrations are additive only (no drops) — they are safe to run on an existing database.
